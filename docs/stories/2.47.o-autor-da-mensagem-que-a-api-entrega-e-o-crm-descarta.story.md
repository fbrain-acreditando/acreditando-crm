# Story 2.47 — O autor da mensagem que a API entrega e o CRM descarta

**Status:** Draft
**Epic:** 2 — Qualificação automática de leads (CRM Acreditando)
**Criada:** 2026-08-19 · **Agente:** @sm (River)
**Nasce de:** story 2.46 (AC0) — a separação IA × pessoa foi entregue por **estimativa** porque o
dado real está sendo jogado fora.

---

## História

**Como** Filipe, lendo o painel,
**quero** que "mensagens da IA" e "mensagens da pessoa" sejam **medição, não estimativa**,
**para que** o número não dependa de um corte que erra sempre que a IA fala depois da transferência.

---

## Contexto medido (2026-08-19)

A 2.46 entregou os dois cards por **corte da transferência**, com a ressalva escrita na tela. O
motivo está medido:

| Fato | Número |
|---|---|
| Mensagens de saída com `sender_type` **NULL** | **8.355** de 8.386 (99,7%) |
| Marcadas como `user` | 26 |
| Marcadas como `ai` ou `agent` | **0** |

A Fernanda responde **dentro do GPT Maker**. Comparando os payloads das mensagens **antes × depois**
da transferência, eles são **idênticos**: mesmo `role: assistant`, mesmo `assistantId`. Enumerei as
**29 chaves** que aparecem em 14.882 eventos — nenhuma distingue autor.

### 🔑 Mas o dado existe — na API, não no webhook

```ts
// lib/messaging/providers/whatsapp/gptmaker.provider.ts
export interface GptMakerMessage {
  role?: string;
  userId?: string | null;   // ← candidato a discriminador (null = IA?)
}
export interface GptMakerChat {
  humanTalk?: boolean;      // "true = atendimento está com humano (IA pausada)"
}
```

E a rota `app/api/messaging/channels/[id]/gptmaker/sync/route.ts` **chama `GET /v2/chat/{id}/messages`,
recebe esse `userId` e o descarta** — o insert não grava `sender_type` nem `userId`.

O webhook (`supabase/functions/messaging-webhook-gptmaker`) também não grava `sender_type` — e, no
caso dele, o campo nem chega.

---

## AC0 — a medição que precede qualquer código

- **AC0.1** — Confirmar **na API real** que `userId` distingue: buscar mensagens de uma conversa
  **transferida** e verificar se as posteriores à transferência têm `userId` preenchido e as
  anteriores não. **Se não distinguir, a story morre aqui** — e o corte da 2.46 continua sendo o
  melhor disponível.
- **AC0.2** — Medir quantas das 8.386 mensagens são recuperáveis pela API (a sync tem limite de
  chats; medido em 04/08: de 4.000 chats, 151 traziam conteúdo).

## Critérios de Aceite

- **AC1** — A rota de sync grava `sender_type` (`'ai'` ou `'user'`) e o `userId` da origem em
  `metadata`, para toda mensagem importada.
- **AC2** — O webhook grava `sender_type` no que der para inferir, e **NULL explícito** onde não
  der — nunca um chute.
- **AC3** — Backfill do histórico até onde a API alcançar, sem sobrescrever `sender_type` já
  gravado por caminho confiável (os 26 `user` do CRM).
- **AC4** — O painel passa a usar a marcação real quando ela existe, e o **corte da transferência
  só como fallback** — com a tela dizendo qual dos dois está em uso.
- **AC5** — Teste de regressão prova que uma mensagem sem discriminador **não** vira `'ai'` por
  omissão. *(O NULL da story 2.44 nasceu exatamente de tratar ausência como valor.)*

## Riscos

| Risco | Mitigação |
|---|---|
| `userId` não distinguir de fato | AC0.1 é gate: mata a story antes de escrever código |
| Backfill sobrescrever dado bom | AC3 proíbe sobrescrever marcação confiável |
| Consumir cota/API de terceiro no backfill | AC0.2 mede o alcance antes |
