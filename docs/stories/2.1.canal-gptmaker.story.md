## Story

**Como** Fernanda (atendimento do Acreditando),
**eu quero** que os leads qualificados pela IA do GPT Maker no WhatsApp entrem sozinhos no funil do CRM,
com o histórico da conversa junto,
**para que** eu pare de classificar lead no olho e passe a ver origem, estrela e estágio no CRM.

**Como** Filipe (admin),
**eu quero** cadastrar o GPT Maker em *Configurações → Integrações → Canais* como qualquer outro canal,
e escolher o funil e o estágio de destino em *Entrada de Leads*,
**para que** a configuração siga o mesmo padrão dos canais que já existem.

---

## Contexto

O WhatsApp do Acreditando **já roda no GPT Maker** (agente "Assistente Virtual do Acreditando").
A IA coleta nome, tipo de lesão, tempo de lesão e região, e **transfere para a Fernanda**.
Hoje esse handoff morre no WhatsApp — o CRM não fica sabendo.

Esta story liga o handoff ao CRM. Estudo completo da API: `docs/research/gptmaker-api-study.md`.
**Modelo escolhido: C (híbrido), Fase 1 = só entrada de leads.**

### AC1 — Provider registrado

- [ ] `getStatus()` lê `GET /v2/workspace/{workspaceId}/channels`, acha o canal por `id` e mapeia `connected: true → 'connected'`, `false → 'disconnected'`

### AC2 — Wizard de configuração
- [ ] Em *Configurações → Integrações → Canais → Adicionar Canal*, "GPT Maker" aparece como opção de WhatsApp
- [ ] Com o `apiToken` preenchido, o wizard **busca e lista** workspaces (`GET /v2/workspaces`), agentes e canais — o usuário escolhe em dropdown, não digita ID na mão
- [ ] Ao salvar, o CRM gera um `webhookSecret` e **exibe a URL do webhook** pronta para colar no GPT Maker
- [ ] Credenciais nunca voltam ao client em listagem (regra existente do CRM)

### AC3 — Webhook de entrada (edge function)
- [ ] Nova edge function `messaging-webhook-gptmaker`, com `verify_jwt = false` no `config.toml`
- [ ] Autenticação **default-deny**: segredo na URL/header comparado com `timingSafeEqual` — sem segredo válido, `401`
- [ ] `channelId` do CRM extraído da URL (mesmo padrão da `messaging-webhook-evolution`)
- [ ] Todo evento gravado em `messaging_webhook_events` com `external_event_id` estável (dedupe)
- [ ] Evento duplicado → `200 { duplicate: true }`, sem reprocessar
- [ ] **Sempre responde HTTP 200** em erro de processamento (evita retry storm)

### AC4 — Lead entra no funil
- [ ] `onFirstInteraction` e `onTransfer` criam/atualizam **contato** (telefone normalizado) e **conversa** (`messaging_conversations`)
- [ ] Se existe `lead_routing_rule` habilitada para o canal, cria o **deal** no funil/estágio configurado (reusa `autoCreateDeal`)
- [ ] O deal guarda `metadata.deal_id` na conversa e a origem (`gptmaker`, `agentId`, `chatId`)
- [ ] `onTransfer` marca a conversa como **"aguardando humano"** (é o sinal de lead quente)
- [ ] Contato **não é duplicado** se já existir com o mesmo telefone na organização

### AC5 — Histórico da conversa
- [ ] Ao criar a conversa, o CRM puxa o histórico via `GET /v2/chat/{chatId}/messages` e grava as mensagens (inbound e outbound) em `messaging_messages`
- [ ] Mensagens de mídia guardam a URL retornada pela API (`imageUrl`, `audioUrl`, `documentUrl`)
- [ ] Paginação respeitada (`page`/`pageSize`), com teto de páginas para não estourar em conversa longa

### AC6 — Entrada de Leads (UI já existente)
- [ ] O card do canal GPT Maker mostra a seção **"Entrada de Leads"** com toggle "Criar deal automaticamente" + seletores **Funil** e **Estágio inicial** — sem código novo de UI, só validar que funciona com o novo provider

### AC7 — Segurança e LGPD
- [ ] `apiToken` nunca aparece em log, nem em resposta de API, nem no client
- [ ] Payload cru gravado em `messaging_webhook_events` **não** guarda o token
- [ ] ⚖️ **Gate LGPD:** a conversa traz **tipo e tempo de lesão = dado de saúde (Art. 11)**. A story **não** libera para produção sem a base legal definida (pendência já aberta em `CRM IA Acreditando`)

## Dev Agent Record (@dev — Dex)

**Commit:** `b28358f` · branch `feat/canal-gptmaker` · **não publicado** (`main` = deploy).

### Decisão de arquitetura que o Modelo A impôs

O Filipe escolheu **canal completo**, mantendo a IA do **GPT Maker** no atendimento e a
IA do **CRM desligada**. Isso não era só uma flag: o webhook da Evolution chama
`triggerAIProcessing()` a cada mensagem inbound, e `agent.service.ts` responde de fato
(`action: 'responded'` → `router.sendMessage`). Copiar o molde sem pensar colocaria
**dois robôs respondendo o mesmo lead**.

Solução em três camadas:
1. A edge function do GPT Maker **nunca** chama `/api/messaging/ai/process`.
2. Conversas nascem com `metadata.ai_paused = true` — `agent.service.ts` já checa esse
   campo e pula (defesa em profundidade, caso alguém dispare o processamento na mão).
3. `ChannelSettings.crmAiEnabled` documenta a intenção. **Virar essa flag é como se faz
   a migração GPT Maker → CRM** que o Filipe planeja — vira decisão, não reescrita.

### Arquivos

| Arquivo | O quê |
|---|---|
| `lib/messaging/providers/whatsapp/gptmaker.provider.ts` | Provider (novo, ~560 linhas): status, envio, start/stop-human, backfill de histórico, configuração de webhooks, discovery para o wizard |
| `supabase/functions/messaging-webhook-gptmaker/parser.ts` | Parser puro e testável (novo) — isolado por ser a peça de maior risco |
| `supabase/functions/messaging-webhook-gptmaker/index.ts` | Edge function (novo): auth default-deny, dedupe, modo captura, handlers de mensagem e transferência |
| `lib/messaging/providers/index.ts` | Registro no factory (`features: ['media']` apenas) |
| `lib/messaging/types/channel.types.ts` | `'gptmaker'` em `CHANNEL_PROVIDERS.whatsapp` + `crmAiEnabled` |
| `features/settings/components/ChannelSetupWizard.tsx` | Passo do GPT Maker + instruções de webhook + segredo auto-gerado + URL com `?key=` |
| `supabase/config.toml` | `verify_jwt = false` |
| `docs/research/gptmaker-api-study.md` | Estudo da API (novo) |

### Desvios conscientes do molde da Evolution

- **`external_contact_id` = chatId** (na Evolution é o telefone). O `chatId` é o único
  identificador aceito por `POST /v2/chat/{chatId}/send-message`.
- **Segredo aceito na query string.** O painel do GPT Maker só permite configurar a URL
  — não há campo de header. Sem isso não haveria autenticação nenhuma.
- **Mensagem para em `status: 'sent'`.** A API não expõe entrega/leitura; marcar
  `delivered` seria mentir para o operador.
- **Parser em módulo separado.** Permite testar no Vitest o único ponto que não dá para
  validar sem a API real.

### Fora de escopo (fica para 2.2)

Rotas de discovery do wizard (`/api/messaging/gptmaker/*`) para escolher workspace/agente/
canal em dropdown. Hoje os 4 IDs são digitados. Depende do token para valer a pena.

**`{"code":"UNAUTHORIZED_NO_AUTH_HEADER"}` HTTP 401** — ou seja, o `verify_jwt=false` do

### Observação de segurança (comportamento herdado, não introduzido)

webhook da Evolution. Um chamador anônimo consegue distinguir "canal existe" de "não
existe" chutando UUIDs. Mantive a paridade com a função existente; se for para mudar,
muda nas duas.
