## História

**Como** Filipe,

**já** extrai,
**para que** o card volte a chegar preenchido e pontuado sem depender do crédito do Google que

---

## De onde veio

A fila interna `ai_pending_lead_scores` tem **91 itens em `failed`** e acumulou **6 falhas só hoje** —
todas pela mesma causa: crédito esgotado no Google desde **18/08**. O CRM tem o mecanismo inteiro
(trigger → fila → endpoint → read-back, stories 2.41 a 2.44) e **nenhuma resposta de modelo** para
colocar dentro dele.

Enquanto isso, o workflow n8n **"05- Transferência"** (`3WO6BcG8M9jVGlnY`) **já faz o trabalho**:
lê a conversa, extrai os campos de qualificação e pontua o lead de **1 a 5** com **chave própria da
OpenAI** — e escreve o resultado num **Google Sheets**.

📌 **O dado existe, pago, todo dia, e morre numa planilha.** Esta story não cria inteligência
nenhuma: cria a **porta** para o que já está pronto entrar no CRM.

---

## Decisões do dono, já tomadas (não reabrir na implementação)

1. **A nota do n8n SUBSTITUI a estrela do CRM.** O Filipe foi avisado de que a escala é diferente
   da interna (a do CRM é "critérios atingidos / critérios conhecíveis") e **assumiu o risco**.
   Por isso a story grava `escala:'n8n:1-5'` em `lead_score_detail` — para que ninguém, daqui a três
   meses, compare 4/5 do n8n com 4/5 do CRM achando que é a mesma régua.
2. **4 campos que o n8n extrai são DESCARTADOS** por não terem destino no CRM:
   `tipo_de_atendimento`, `onde_fez_reabilitacao`, `tipo_avalicao`, `resumo`.
   Eles chegam pela rota, não derrubam a request, e voltam na resposta como
   `skipped: chave_desconhecida`. **Descartar calado seria a mesma classe de silêncio da 2.44.**

## O contrato

**Rota:** `POST /api/public/v1/deals/{dealId}/ai-extraction` · `runtime = 'nodejs'`
Casca **igual** à de `app/api/public/v1/deals/[dealId]/route.ts:18-26` (auth → uuid → admin client).

**Headers:** `X-Api-Key` (obrigatório) · `Idempotency-Key` (opcional).

**Body (Zod v4):**

```ts
const FieldValue = z.object({
  value: z.string().min(1).max(500).nullable(),
  confidence: z.number().min(0).max(1).optional(),
}).strict();

const AiExtractionSchema = z.object({
  custom_fields: z.record(
    z.string().min(1).max(64),
    z.union([z.string().max(500), z.null(), FieldValue])
  ).optional(),
  lead_score: z.object({
    score: z.number().int().min(1).max(5),
    rotulo: z.string().max(80).optional(),
    criterios_atingidos: z.array(z.string().max(120)).max(20).optional(),
    red_flags: z.array(z.string().max(120)).max(20).optional(),
    confianca: z.number().min(0).max(1).optional(),
  }).strict().optional(),
  overwrite: z.boolean().optional(),
}).strict().refine(v => !!v.custom_fields || !!v.lead_score, {
  message: 'custom_fields or lead_score is required',
});
```

**Resposta 200:**

```jsonc
{ "data": {
  "deal_id": "...",
  "custom_fields": { "updated": ["tipoDeLesao"], "skipped": [{ "key": "resumo", "reason": "chave_desconhecida" }] },
  "lead_score": { "applied": true },
  "idempotent_replay": false
}}
```

`reason` ∈ `campo_ja_preenchido` · `chave_desconhecida` · `confianca_baixa` ·
`valor_invalido_para_o_tipo` · `nota_manual`.

| Código | Quando |
|---|---|
| **400** `BAD_REQUEST` | JSON inválido no corpo |
| **401** | o que o `authPublicApi` já devolve |
| **404** `NOT_FOUND` | deal inexistente, de outra organização, ou com `deleted_at` |
| **409** `IDEMPOTENCY_CONFLICT` | mesma `Idempotency-Key`, corpo diferente |
| **422** `VALIDATION_ERROR` | uuid inválido ou corpo que não passa no Zod |
| **500** `DB_ERROR` | erro de banco |

⚠️ **Key desconhecida NÃO derruba a request** — vira `skipped`. O n8n manda 9 campos e só 5 têm
destino; recusar o lote inteiro por causa de `resumo` seria perder os 5 bons.

## 🧱 MIGRATION OBRIGATÓRIA — sem ela, **todo** POST falha

Verificado **no banco de produção**:

```
deals_lead_score_source_check  →  CHECK (lead_score_source IN ('auto','manual'))
```

⇒ **`'n8n'` é REJEITADO hoje.** A migration precisa **dropar e recriar** o CHECK com
`('auto','manual','n8n')`. Este é o item que transforma a story de "funciona no teste" em
"funciona em produção" — e é o primeiro passo da implementação, não o último.

A mesma migration cria `public.public_api_idempotency`:

| Coluna | |
|---|---|
| `organization_id`, `endpoint`, `idempotency_key` | chave do registro — **unique em (organization_id, endpoint, idempotency_key)** |
| `request_hash` | hash do corpo, para separar replay de conflito |
| `response_status`, `response_body` | o que devolver no replay |
| `created_at` | |

**RLS enabled, sem policy** ⇒ só `service_role` enxerga.

Fluxo espelha `supabase/functions/webhook-in/index.ts:209-249`: **INSERT primeiro**; violação de
unique → **SELECT** → hash igual = **replay** (devolve a resposta guardada), hash diferente = **409**.

## As 8 regras de gravação (cada uma com precedente no código)

| # | Regra | Precedente |
|---|---|---|
| 1 | Não sobrescreve campo já preenchido (salvo `overwrite: true`) — **reusar** `isBlank`, não reimplementar | `lib/ai/extraction/customFields.service.ts:313` |
| 2 | Confiança mínima **0,6** quando vier; ausente conta como **1** | `MIN_CONFIDENCE_TO_STORE` — `customFields.service.ts:51` |
| 3 | Coagir o valor pelo tipo do campo via `coerceValueForField` | `customFields.schemas.ts:87` |
| 4 | Só keys existentes em `custom_field_definitions` (org + `entity_type='deal'`), query **igual** à existente | `customFields.service.ts:106-113` |
| 5 | Proveniência em `deals.ai_extracted.customFields[key]` = `{value, confidence, reasoning:'n8n', extractedAt, source:'n8n'}` | forma de `customFields.service.ts:248-253` |
| 6 | A nota **nunca** sobrescreve manual: `.or('lead_score_source.is.null,lead_score_source.neq.manual')` — **copiar EXATAMENTE, com o `is.null`** | `processarItemDaFila.ts:277-291` (e a story 2.44) |
| 7 | **Read-back:** `.select('id')` no UPDATE; 0 linhas ⇒ `applied:false, reason:'nota_manual'` | `processarItemDaFila.ts:296-305` |
| 8 | Gravar `pontuada_pela_ia_em` — impede a fila interna de repontuar e sobrescrever a nota do n8n | `lib/ai/scoring/processarItemDaFila.ts:270` |

**`lead_score_known = 5`** — obrigatório, não decorativo:
- o CHECK do banco exige `lead_score <= lead_score_known`;
- `null` renderiza **"★ 4/0"** na tela (`features/boards/components/Kanban/DealCard.tsx:227`);
- a nota manual já grava 5 (`features/boards/components/Modals/DealDetailModal.tsx:472`), então a rota fica coerente com o que existe.

## Critérios de aceite

- [ ] **AC1 — Migration do CHECK.** `deals_lead_score_source_check` recriado com
      `('auto','manual','n8n')`, com read-back da definição relida do `information_schema` (não da
      resposta do executor). **Enquanto este AC estiver aberto, nenhum POST com `lead_score` funciona.**
- [ ] **AC2 — Migration da idempotência.** `public.public_api_idempotency` criada com o unique em
      `(organization_id, endpoint, idempotency_key)`, **RLS enabled e sem policy** (só `service_role`).
- [ ] **AC3 — Auth.** Sem `X-Api-Key` válida a rota devolve o **401** do `authPublicApi`, e
      **nenhuma query de escrita acontece antes** da checagem.
- [ ] **AC4 — Validação.** `dealId` fora do formato uuid ⇒ **422**; corpo que não passa no Zod ⇒
      **422** com `code: VALIDATION_ERROR`; JSON malformado ⇒ **400** `BAD_REQUEST`; corpo sem
      `custom_fields` **e** sem `lead_score` ⇒ **422** (o `refine`).
- [ ] **AC5 — Escopo do deal.** Deal inexistente, de **outra organização**, ou com `deleted_at`
      preenchido ⇒ **404** `NOT_FOUND` — os três casos com teste próprio, porque o admin client
      **ignora RLS** e só o filtro explícito de `organization_id` separa uma org da outra.
- [ ] **AC6 — Regra 1: não sobrescreve o que já está preenchido.** Campo com valor não muda;
      com `overwrite: true` muda; o campo pulado volta em `skipped` com `campo_ja_preenchido`.
      Usa o `isBlank` de `customFields.service.ts:313` — **reuso, não cópia**.
- [ ] **AC7 — Regra 2: confiança.** `confidence < 0.6` ⇒ `skipped: confianca_baixa`;
      `confidence` ausente ⇒ trata como **1** e grava; string crua (sem objeto) ⇒ grava.
- [ ] **AC8 — Regra 3: coerção por tipo.** Valor passa por `coerceValueForField`; valor que o tipo
      recusa ⇒ `skipped: valor_invalido_para_o_tipo` (**não** 422 — não derruba o lote).
- [ ] **AC9 — Regra 4: só key conhecida.** Keys buscadas em `custom_field_definitions` filtrando
      organização **e** `entity_type='deal'`; key desconhecida ⇒ `skipped: chave_desconhecida`, com
      **200** na request. Teste cobre exatamente os 4 campos descartados do n8n.
- [ ] **AC10 — Regra 5: proveniência.** `deals.ai_extracted.customFields[key]` recebe
      `{value, confidence, reasoning:'n8n', extractedAt, source:'n8n'}` — e **o restante de
      `ai_extracted` sobrevive** (ver AC17).
- [ ] **AC11 — Regra 6: nota manual intocável.** O UPDATE usa
      `.or('lead_score_source.is.null,lead_score_source.neq.manual')` **literalmente**. Testes:
      card com `lead_score_source = NULL` **recebe** a nota (o caso da 2.44), card `auto` recebe,
      card `manual` **não** recebe.
- [ ] **AC12 — Regra 7: read-back.** O UPDATE carrega `.select('id')`; **0 linhas** ⇒ resposta
      `lead_score: { applied:false, reason:'nota_manual' }`, e a request continua **200**.
- [ ] **AC13 — Regra 8: carimbo.** `pontuada_pela_ia_em` gravado junto com a nota, para que a fila
      interna não repontue e apague o que o n8n trouxe.
- [ ] **AC14 — Escala explícita.** `lead_score_known = 5` sempre; `lead_score_detail` guarda
      `escala:'n8n:1-5'` mais `rotulo`, `criterios_atingidos`, `red_flags` e `confianca` quando vierem.
- [ ] **AC15 — Idempotência.** Mesma `Idempotency-Key` + mesmo corpo ⇒ **200** com
      `idempotent_replay: true` e **nenhuma segunda escrita** no deal. Mesma key + corpo diferente ⇒
      **409** `IDEMPOTENCY_CONFLICT`. Sem header ⇒ processa normalmente.
- [ ] **AC16 — Lógica testável sem HTTP.** As regras vivem em `lib/public-api/aiExtraction.ts`
      (padrão de `lib/public-api/dealsMoveStage.ts`); a rota é casca fina. Se rota e função
      divergirem, **a função é a verdade** (contrato herdado da 2.44).
- [ ] **AC17 — Testes.** `test/publicApi.aiExtraction.test.ts` cobrindo, no mínimo: 401 · 422 (uuid,
      Zod, refine) · 400 · 404 (inexistente / outra org / deleted_at) · as 5 razões de `skipped` ·
      `overwrite` · nota em card `NULL`/`auto`/`manual` · read-back de 0 linhas · replay · 409 ·
      **merge de `ai_extracted` sem perder chave anterior** · `lead_score_known = 5`.
- [ ] **AC18 — OpenAPI.** Novo path em `lib/public-api/openapi.ts:589` e
      `lib/supabase/deals.ts:73` com o tipo `'auto' | 'manual' | 'n8n' | null`.
- [ ] **AC19 — Gates.** `lint 0` · `typecheck 0` · suíte inteira verde com os testes novos somados
      ao total anterior (declarar o delta, como nas stories 2.44 e 2.48).
- [ ] **AC20 — Read-back em produção (Rule 7).** Depois da migration: um POST real do n8n num deal
      de teste e **releitura no banco** de `lead_score`, `lead_score_known`, `lead_score_source`,
      `pontuada_pela_ia_em`, `ai_extracted` e dos campos custom gravados. *"A API respondeu 200"*
      **não** fecha este AC.

### Sobre a escala (dívida registrada, não escondida)

A nota do n8n é **1 a 5 por julgamento de modelo**; a do CRM é **critérios atingidos sobre
conhecíveis**. Um "3" de cada lado **não quer dizer a mesma coisa**. O Filipe aceitou a substituição
sabendo disso. `lead_score_detail.escala = 'n8n:1-5'` é o que permitirá, no futuro, separar as duas
populações sem arqueologia.
