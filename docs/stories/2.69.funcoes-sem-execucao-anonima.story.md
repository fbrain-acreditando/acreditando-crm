## O que já existe (lido na `origin/main` = `d60b02c`)

### A função

`supabase/migrations/20251201000000_schema_init.sql:905`:

```sql
CREATE OR REPLACE FUNCTION cleanup_rate_limits(older_than_minutes INTEGER DEFAULT 5)
RETURNS INTEGER LANGUAGE plpgsql SECURITY DEFINER SET search_path = public AS $$
...
    DELETE FROM public.rate_limits
    WHERE created_at < NOW() - (older_than_minutes || ' minutes')::INTERVAL;
```

- `SECURITY DEFINER`: roda com o poder do dono e **ignora a RLS** de `rate_limits`.
- **Não confere quem chama** (nenhum `auth.uid()`, nenhum `auth.role()`).
- **Ninguém no código a chama:** `git grep cleanup_rate_limits origin/main` fora das migrations dá vazio. Nenhum dos 6 `cron.schedule` versionados a usa. 🆕 **v0.3 (T0, A5):** nenhum job do `pg_cron` de produção a chama, e os logs de 9 dias não mostram chamada por `/rpc`.

### Por que a correção de 23/02 não valeu

`supabase/migrations/20260223000001_fix_rpc_anon_access.sql`:

```sql
-- Root cause: PostgreSQL grants EXECUTE to PUBLIC by default on all functions.
REVOKE ALL ON FUNCTION public.cleanup_rate_limits(INTEGER)    FROM PUBLIC;
GRANT EXECUTE ON FUNCTION public.cleanup_rate_limits(INTEGER) TO service_role;
```

O diagnóstico estava **incompleto**. O Postgres puro dá EXECUTE a `PUBLIC`, mas o Supabase **também** tem privilégios padrão no schema `public` que dão EXECUTE **pelo nome** a cada papel. O @qa leu em `pg_default_acl`, e o T0 confirmou (A8): `{postgres=X, anon=X, authenticated=X, service_role=X}`. Então:

1. `REVOKE … FROM PUBLIC` tira só a permissão do grupo "todo mundo". A permissão **nominal** do `anon` continua lá.
2. O `GRANT … TO service_role` **não restringe** nada: só soma. `authenticated` também continua com a permissão nominal.
3. Prova viva: `mark_deal_lost` (revogada só de `PUBLIC` nessa mesma migration) dá `has_function_privilege('anon', …) = true` (T0: as 21 do D2 estão todas com `anon = true`).

A migration de 23/02 **rodou**. Ela só não fazia o que o comentário dizia.

### Como a migration é aplicada (v0.2, R5; 🆕 medido no T0)

`scripts/db/aplicar-migracao.mjs` manda o arquivo inteiro numa chamada só para a API de gestão do Supabase (`POST /v1/projects/<ref>/database/query`, body `{ query: sql }`, **sem** `read_only`). Três consequências:

1. **Recusa `DROP`/`TRUNCATE` no código** (comentários são ignorados). Esta migration não tem nenhum dos dois. ⚠️ O ensaio da função descartável (D4) usa `CREATE` e depois o `ROLLBACK` a desfaz; ele **não** passa por este script, roda só no T4.
2. **O read-back do script olha só colunas** (`ADD COLUMN IF NOT EXISTS`). Para esta migration ele vai mostrar "Colunas prometidas: (nenhuma detectada)", ou seja, **não prova nada**. A única prova é o AC2.
3. 🆕 **v0.3 (T0, A10): o arquivo roda numa transação só.** Medido com o teste da Dara: depois de `select pg_sleep(0.3);`, o comando seguinte deu `clock_timestamp() - now()` = **0,302 s** (se cada comando fosse uma transação, daria perto de 0). O teste antigo da v0.2 (`now() = statement_timestamp()`) **não serve**: num texto com vários comandos mandado de uma vez, `statement_timestamp()` é a hora em que o texto inteiro chegou, então ele dá `true` sempre. **Ressalva:** a medida foi feita pelo caminho `read_only`, não pelo caminho do script. 🆕 **v0.4 (C9):** a prova que fecha a ressalva é **o mesmo teste pelo caminho do script** — mandar pela API de gestão, **sem** `read_only` (como o `aplicar-migracao.mjs` faz), o texto `select pg_sleep(0.3); select extract(epoch from clock_timestamp() - now());`. Ele não escreve nada, mas usa o caminho de escrita, então **pede o OK do Filipe**. ≈ 0,3 s ⇒ esse caminho também roda o texto como uma transação só, e uma assinatura errada derruba o arquivo inteiro. Perto de 0 ⇒ esse caminho roda um comando por transação, a migration **passa a precisar** de `BEGIN;`/`COMMIT;`: **parar e voltar ao @sm**. Um ensaio com assinatura errada dentro de `BEGIN; … ROLLBACK;` **não** prova isso (o próprio `BEGIN` do ensaio junta tudo numa transação). **Consequência (se ≈ 0,3 s):** a migration **não** leva `BEGIN;`/`COMMIT;`, e o ensaio do T4 fica simples (`BEGIN;` + arquivo inteiro + `ROLLBACK;`, sem `COMMIT` escondido).
4. 🆕 **v0.3 (T0, A9): o papel que aplica é `postgres`**, por prova **indireta**: as funções que o script criou em 03/11 (2.67: `texto_de_busca(text)`; `find_or_create_contact_por_variantes(…)`) têm dono `postgres`, e quem cria uma função vira o dono dela. O `current_user` do caminho do script **não** foi lido direto (com `read_only: true` a API troca o papel para `supabase_read_only_user`).

### D3 — O teste que impede a volta do defeito (v0.2, C6)

Um teste do vitest que **lê todas as migrations** (sem banco, como o `lib/supabase/ondeMora.test.ts` já faz com `readFileSync`/`readdirSync`), na **ordem dos nomes dos arquivos**, e falha quando uma função `public` com `SECURITY DEFINER`, que não é de gatilho, **não** tem `REVOKE … FROM … anon` pelo nome (mesma assinatura quando ela vier escrita) **no mesmo arquivo ou num arquivo posterior ao último `CREATE` dela**. A única saída é a **lista de exceções com o motivo escrito**: `validate_api_key` e `is_instance_initialized` (uso sem login, S4) e, até a 2.70, `resgatar_itens_presos` (S5).

- **Por que a ordem:** "tem `REVOKE` em alguma migration" deixa passar a função revogada e **depois** recriada. A regra é conservadora: um `CREATE OR REPLACE` futuro vai exigir repetir o `REVOKE`, e é isso que queremos.
- 🆕 **v0.3 — o caso real:** `get_user_org_id()` tem `REVOKE … anon` em `20260224000000:120` e `CREATE OR REPLACE` **depois**, em `20260403000000:67`. Com as migrations de hoje (até `20261103180000`), o teste **tem que reprovar** nela. Com a migration nova da 2.69 (que repete o `REVOKE` depois), **tem que passar**. Isso deixa de ser hipótese: é a prova de que a regra de ordem funciona (ver AC4).
- 🆕 **v0.4 (C7) — o limite do caso real:** o AC4 lê o repo. Ele reprova a `get_user_org_id` pela ordem dos arquivos, mas o banco abriu por outro motivo (a `20260224000000` nunca rodou). Contra a diferença repo × banco, quem protege é o AC2. (Se a `20260403000000` não tivesse o `CREATE OR REPLACE`, o teste passaria verde com o banco aberto.)
- **Estilos de SQL que o leitor precisa cobrir** (todos existem hoje): `SECURITY DEFINER` **depois** do corpo (`$$ LANGUAGE plpgsql SECURITY DEFINER;`, em `trigger_hitl_alerts` e `expire_old_pending_advances`); função **sem** `public.` (`cleanup_rate_limits`, `log_audit_event`); `RETURNS TABLE(...)`; `RETURNS trigger` (vira exceção automática); `REVOKE` **sem** assinatura (`custom_access_token_hook`); comentário `--` com a palavra "SECURITY DEFINER" (não conta); minúsculas (`create or replace function`); 🆕 função `LANGUAGE sql` `STABLE` (`get_user_org_id`).
- **Controle positivo obrigatório:** o teste afirma que o conjunto de funções `SECURITY DEFINER` que achou **contém** pelo menos `cleanup_rate_limits`, `trigger_hitl_alerts`, `expire_old_pending_advances`, `update_message_status_if_newer`, `validate_api_key`, `get_lista_da_fila` e 🆕 `get_user_org_id`, e que o total é **≥ 38** (o número do código, igual ao de produção no T0). Motivo: na validação, a primeira versão do leitor do @po **não enxergou** a `cleanup_rate_limits` nem a `trigger_hitl_alerts`. Leitor cego passa verde.

### D4 — O padrão do banco (Q3), do jeito que fecha de verdade (v0.2, C3; 🆕 confirmado no T0)

- No Postgres, o privilégio padrão **por schema** é **somado** ao padrão **geral** do tipo de objeto. 🆕 **v0.3 (T0, A7):** **não existe** linha geral (`defaclnamespace = 0`) para ninguém, então vale o embutido do Postgres: **EXECUTE para `PUBLIC`**. Prova viva: `get_lista_da_fila`, `get_fila_de_atendimento`, `trigger_hitl_alerts` etc. têm `=X/postgres` no `proacl`. E (A8) o padrão do schema `public` do `postgres` dá EXECUTE **nominal** a `anon`. A `texto_de_busca(text)` da 2.67 só está fechada (`{postgres=X, authenticated=X, service_role=X}`, sem `=X/`) porque foi revogada à mão.
- Bloco próprio, no fim da migration:
  ```sql
  ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public REVOKE EXECUTE ON FUNCTIONS FROM anon;
  ALTER DEFAULT PRIVILEGES FOR ROLE postgres REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC;   -- sem IN SCHEMA
  ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public GRANT EXECUTE ON FUNCTIONS TO authenticated, service_role;
  ```
  🆕 **v0.3: as duas primeiras linhas são necessárias, cada uma fecha uma porta diferente.** A 1ª tira o `anon` nominal do padrão do schema (A8). A 2ª cria a linha geral que hoje não existe e tira o `PUBLIC` (A7). Só uma delas deixaria a função nova aberta pela outra porta. A 3ª é **redundante hoje** (os dois papéis já estão no padrão do schema), mas é inofensiva e deixa escrita a decisão "função nova nasce para logado e para o sistema". O @qa confere no T5 se ela fica.
- 🆕 **v0.3 — permissão, provada só de forma indireta (A9):** o script aplica como `postgres` (dono das funções que ele criou em 03/11), e um papel sempre pode alterar os **próprios** padrões (`FOR ROLE <ele mesmo>`) sem ser superusuário. **A prova direta é o T4**: rodar o bloco dentro do `BEGIN; … ROLLBACK;`. Se der `permission denied`, o bloco **sai** da migration e a story registra isso.
- **A prova de que fecha não é ler o `pg_default_acl`.** É criar uma **função descartável** dentro do `BEGIN; … ROLLBACK;` do ensaio (T4), como `postgres`, e ler `has_function_privilege('anon', '<a descartável>', 'EXECUTE') = false` e `has_function_privilege('authenticated', …) = true`.
- **Limite, escrito para ninguém se enganar:** o padrão só vale para funções criadas **pelo papel** `postgres`. 🆕 O padrão do `supabase_admin` no `public` **não** pode ser mudado (o `postgres` não é membro dele), mas hoje só afeta as 4 funções do `unaccent`. Em qualquer caso, a proteção real é o teste do AC4.

4. **Leitor do teste, regra de ordem:** a função fica fechada se houver `REVOKE … anon` (pelo nome; com assinatura igual, ou sem assinatura) **no mesmo arquivo ou num arquivo posterior** ao último `CREATE`. Dentro de um arquivo, as permissões contam **depois** da estrutura (CREATE/DROP/RENAME). 6. **`GRANT … TO anon` ou `TO PUBLIC` depois do `REVOKE` reabre** a função no leitor (conservador; um caso de controle prova).
7. **Gatilho (`RETURNS trigger`) é exceção automática**; só o schema `public` conta (sem schema = `public`).
8. **Guarda a mais (AC1):** o teste confere, para cada uma das 22, os papéis exatos do `REVOKE` e do `GRANT` (só sistema / logado / #22 com `service_role`), e que a migration não cita nenhuma das 3 exceções.
