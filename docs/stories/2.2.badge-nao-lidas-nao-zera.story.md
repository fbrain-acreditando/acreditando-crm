## Story

**Como** Fernanda (comercial, ~700 leads/mês na tela de Mensagens),
**quero** que a conversa pare de mostrar o contador de mensagens não lidas depois que eu a abro,
**para que** eu consiga usar o badge como fila de trabalho — hoje ele mostra tudo como pendente e eu perco o que ainda não atendi.

---

## Contexto / Sintoma relatado

> "Tem um bug nas mensagens. Após abertas ainda ficam com o ícone com o número de mensagens não visualizadas."

O badge é a **única** indicação visual de fila na tela de mensagens (`ConversationItem.tsx:122`), e alimenta também o contador do menu lateral (`Layout.tsx:304`). Com ele travado, a tela não distingue lead atendido de lead esperando.

---

## Causa raiz (confirmada em código, não hipótese)

`lib/query/hooks/useConversationsQuery.ts:364-379` — o `onMutate` de `useMarkConversationRead`:

```ts
queryClient.setQueriesData(
  { queryKey: queryKeys.messagingConversations.all },   // ← filtro por PREFIXO
  (old: ConversationView[] | undefined) => {
    if (!old) return old;                                // ← guarda insuficiente
    return old.map((conv) => ...);                       // ← estoura em cache não-array
  }
);
```

1. `messagingConversations.all` é o prefixo `['messagingConversations']`. O filtro casa **três** famílias de cache: a lista (`filtered(...)` → array), o detalhe (`detail(id)` → **objeto** `ConversationView`) e o contador (`unreadCount()` → **number**).
2. Quando o efeito dispara, o cache `detail(id)` **sempre existe** — é dele que sai o `unreadCount > 0` que autoriza a chamada (`MessagingPage.tsx:168`). `!old` é `false` para um objeto ⇒ executa `old.map` ⇒ **`TypeError: old.map is not a function`**.
3. `@tanstack/query-core@5.96.2`, `mutation.js:102` e `:115` — `await this.options.onMutate?.()` roda **antes** de `await this.#retryer.start()`. Erro em `onMutate` cai no `catch` da linha `:146` e a **`mutationFn` nunca executa** ⇒ o `UPDATE ... SET unread_count = 0` **nunca chega ao banco**.
4. O `onSettled` roda no caminho de erro e invalida a lista ⇒ refetch traz o `unread_count` original ⇒ novo objeto `selectedConversation` ⇒ o efeito da `MessagingPage.tsx:167` dispara de novo ⇒ **laço de tentativas enquanto a conversa estiver aberta**, todas falhando em silêncio (`mutate` sem `onError`).

**A prova do descuido está no mesmo arquivo:** `useUpdateConversation` (`:309-317`) faz o mesmo `setQueriesData` **com** a guarda `if (!Array.isArray(old)) return old;` e o comentário *"Guard against non-array entries (e.g. detail queries return ConversationView | null)"*. `MessagingPage.tsx:107` também guarda. Só o `useMarkConversationRead` não.

**Cobertura de testes hoje:** nenhuma. `grep` por `markAsRead`/`useMarkConversationRead` em `test/`, `features/` e `lib/` não retorna **nenhum** arquivo `.test.ts(x)`.

### Risco de segunda camada (a confirmar após o fix)

`supabase/migrations/20260205100000_create_messaging_system.sql:322-341` — a policy de UPDATE de `messaging_conversations` exige **admin** ou pertencer ao `business_unit_members` do `business_unit_id` da conversa. Para usuário não-admin em conversa com `business_unit_id NULL`, o `UPDATE` direto afeta **0 linhas sem erro** (PostgREST não reclama). Hoje isso seria **invisível**: a mutation não confere linhas afetadas (`.update()` sem `.select()`).

⚠️ Ou seja: corrigir só o `onMutate` pode **destravar a escrita e ainda assim o badge não zerar** para quem não é admin. Por isso o AC4.

## Critérios de Aceite

- **AC1** — Abrir uma conversa com `unreadCount > 0` zera o badge da lista **imediatamente** (otimista) **e** o valor permanece 0 após o refetch do `onSettled` (ou seja, o banco foi realmente atualizado).
- **AC2** — O `onMutate` **não lança** quando os caches `detail(id)` (objeto) e `unreadCount()` (número) estão populados; caches não-array são devolvidos intactos.
- **AC3** — O contador do menu lateral (`Layout.tsx`, via `useUnreadCount`) reflete a baixa após a leitura.
- **AC4** — A escrita passa a ser **verificável** (Rule 7 aplicada no código): a `mutationFn` confere que a linha foi de fato afetada e **falha alto** (erro) em vez de retornar sucesso silencioso quando 0 linhas mudam — cobrindo o cenário de RLS.
- **AC5** — Testes de regressão cobrindo: (a) `onMutate` com cache misto (lista + detail + unreadCount) sem exceção; (b) a `mutationFn` sendo efetivamente chamada; (c) 0 linhas afetadas ⇒ erro.
- **AC6** — Gates: `lint` 0 · `typecheck` 0 · suíte verde e **maior** que 471 · `npm run build` ok.

## Fora de escopo (registrado, não corrigido aqui)

- 🧟 **`MessagingContext.tsx` é código morto** — nenhum layout monta `MessagingProvider`, `useMessaging()` não é chamado em lugar nenhum. Ele carrega uma **segunda** `useMarkConversationRead` (a versão RPC de `useMessagingConversationsQuery.ts:354`).
- ⚠️ **Colisão de queryKey:** `useUnreadCount` (`useConversationsQuery.ts:245`, count SQL) e `useUnreadConversationCount` (`useMessagingConversationsQuery.ts:273`, RPC `get_messaging_unread_count`) usam a **mesma key** `['messagingConversations','unreadCount']` com `queryFn` e `staleTime` diferentes. Hoje não colidem porque o segundo não é montado — vira bug no dia em que alguém montar o provider.
- 🔁 **A RPC `mark_conversation_read` existe** (`20260223000001_fix_rpc_anon_access.sql:223`, `SECURITY DEFINER`, filtra por org) e **não é usada pela tela**. Migrar para ela contornaria a RLS de business unit — é decisão de produto/segurança, não deste bugfix.
- 🔍 O barrel `lib/query/hooks/index.ts:125` exporta a versão **RPC** de `useMarkConversationRead`; importar de `@/lib/query/hooks` entrega hook diferente do que a `MessagingPage` usa. Armadilha para a próxima pessoa.
