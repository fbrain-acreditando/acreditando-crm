## 🔍 AC0 — RODADO antes de escrever

### Passo 1 — eliminar o caminho da mutação

Teste com `QueryClient` real, `useDealsByBoard` como observer ativo e um servidor falso: otimismo → escrita → `invalidate` → refetch. **O cache termina com o valor NOVO.** ⇒ o caminho da mutação está limpo, e a perda acontece **depois** dele. Na janela seguinte só existe um escritor: o **Realtime**.

### Passo 2 — os dois defeitos, provados por teste

🔴 **(A) A tradução banco→app do Realtime era uma lista escrita à mão.**

```js
// useRealtimeSync.ts:860-898 (antes) — normalizava 7 campos
updated_at · created_at · stage_id · is_won · is_lost · closed_at · last_stage_change_date
// e no fim:  return { ...deal, ...normalizedData }
```

`custom_fields` não estava na lista ⇒ entrava **como chave nova em snake_case**, e o `customFields` que a tela lê **ficava com o valor velho**. Provado:

```
resultado.custom_fields → { ondeReside: 'Guarulhos' }   ← chegou
resultado.customFields  → { ondeReside: 'Santos'    }   ← e a tela vê o velho
```

Isso explica os dois sintomas com a mesma causa: *"some"* é o valor velho **vazio**; *"volta para o antigo"* é o valor velho **preenchido**.

🔴 **(B) A decisão de aplicar o update olhava só o estágio.**

```js
// useRealtimeSync.ts:698 (antes)
if (currentStatus === incomingStatus) return old;   // descarta a LINHA INTEIRA
```

A regra confundia **movimentação** com **atualização**: se o card não mudou de coluna, o evento inteiro ia fora. ⇒ toda edição que não move o card — valor, título, campos personalizados, motivo de perda — **era descartada**, viesse de qualquer aba ou usuário.

### Passo 3 — a varredura da classe (é o que a pergunta do Filipe pedia)

> *"achem uma forma de resolver isso de uma vez por todas em todo o CRM"*

🔑 **O defeito nunca foi `custom_fields`. Foi existirem DUAS traduções** do mesmo dado: a canônica (`transformDeal`, que todo `fetch` usa) e uma cópia manual no Realtime. **A cópia nasce desatualizada no dia em que alguém adiciona uma coluna — e falha calada.**

Varrido `payload.new as` no repo inteiro:

| Local | Estado |
|---|---|
| `useRealtimeSync.ts:~860` — UPDATE de deals | 🔴 lista de **7** campos → **corrigido** |
| `useRealtimeSync.ts:~487` — INSERT de deals | 🔴 **terceira** tradução, de **12** campos → **corrigido** |
| `useRealtimeSync.ts:693` — deal ausente do cache | 🔴 empurrava a **linha crua** (`[...old, newData]`) → **corrigido** |
| `useRealtimeSync.ts:298` — mensagens | ✅ já usava `transformMessage`, a canônica |

🪤 **A tradução do INSERT ainda tinha um erro próprio:** mapeava `company_id`, **coluna que não existe** na tabela (a real é `client_company_id`). Código morto que ninguém percebeu porque nada quebra — só não funciona.

📌 **E este padrão já estava DOCUMENTADO**, na story **2.14**: *"linha CRUA do Postgres"*. Ficou escrito e não foi consertado. É o irmão exato da lição de 04/08 — *armadilha documentada não é armadilha resolvida*.

## 🔧 O conserto

**`lib/realtime/normalizeDealRow.ts`** (novo) — três funções pequenas e testáveis:

| Função | O que faz |
|---|---|
| `normalizarDealDoRealtime(linha)` | Traduz usando **`transformDeal`** — a MESMA função do fetch. Zero listas manuais |
| `mesclarDealDoRealtime(cache, linha)` | Espalha o traduzido **por cima** do cache, preservando `companyName`, `contactName`, `stageLabel`, `items` e `owner`, que a tabela `deals` não carrega |
| `linhaDoRealtimeEhMaisNova(cache, linha)` | Freshness por **`updated_at`**, não por estágio |

⚖️ **A proteção que a regra (B) tentava dar continua — e melhor.** O medo original era legítimo: o card *"pular de volta"* quando um evento atrasado chega por cima de um update otimista. Só que o **estágio** era o proxy errado. Agora um evento fora de ordem chega com `updated_at` mais antigo que o do cache e é descartado — protege o mesmo caso **sem** cegar o resto da linha.

📉 **Saldo:** `useRealtimeSync.ts` foi de **1.019 para 732 linhas** (−287). A maior parte era log de depuração dentro da decisão.

## Riscos

| Risco | Mitigação |
|---|---|
| Relógio do cliente à frente do servidor faz o próprio evento parecer "antigo" e ser descartado | Sem efeito prático: o update otimista **já aplicou o mesmo valor**. O caso que importa (outra aba/usuário) traz timestamp do servidor nos dois lados |
| `transformDeal` devolve `items: []` para uma linha do Realtime (que não traz `deal_items`) | `normalizarDealDoRealtime` **remove `items` e `owner`** antes de mesclar — travado pelo AC4 |
| Aplicar mais eventos que antes aumenta repintura | Aplicar era o comportamento **pretendido**; o que havia era perda silenciosa. E o merge continua sendo `setQueryData` targeted, sem invalidação |
